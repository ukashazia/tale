# Contributing to Tale

Thank you for helping improve Tale. Contributions can include bug reports,
feature ideas, documentation, tests, and code.

Tale is a keyboard-first terminal application for Tailscale networks. Changes
should keep the interface predictable, protect sensitive network data, and work
well in both local-client and tailnet-wide modes.

## Before you start

For a small, focused fix, feel free to open a pull request directly. For a new
feature, user-visible behavior change, or architectural change, open an issue
first so the problem and intended behavior can be agreed on before substantial
work begins.

When reporting a bug, include:

- what you expected to happen;
- what happened instead;
- the Tale version, operating system, terminal, and Tailscale version;
- the smallest sequence of steps that reproduces the problem; and
- a redacted diagnostic report, when relevant, produced with
  `tale doctor --output support.json`.

Inspect diagnostic output before sharing it. Never include access tokens,
OAuth client secrets, credential files, private keys, or real tailnet data in
an issue, test, fixture, screenshot, or pull request.

## Development environment

The supported development environment is the repository's Nix flake. It pins
Rust and the tools used by CI.

You will need [Nix](https://nixos.org/download/) with flakes enabled.

From a checkout, enter the development shell:

```sh
nix develop
```

You can also run a command without entering an interactive shell:

```sh
nix develop --command just check
```

## Version-control workflow

Create a focused branch for your contribution:

```sh
git switch -c fix/describe-the-problem
```

Use clear commit messages, strictly following the
[Conventional Commits](https://www.conventionalcommits.org/) format:

```text
fix: describe the problem being fixed
```

Common commit types include `fix`, `feat`, `docs`, `test`, and `refactor`.

Keep each pull request focused on one concern. Do not include drive-by cleanup,
unrelated formatting, or other unrelated changes.

Review your work before submitting it:

```sh
git status
git diff
```

## Making changes

Prefer the smallest complete solution that works end to end. Keep concerns
separate and use the project's existing dependencies and patterns before
adding new abstractions or packages. If an existing library may already solve
the problem, check its documentation and types before reimplementing it.

Do not add compatibility layers, fallback paths, or migrations unless the
current requirement explicitly calls for them. Remove obsolete paths when
replacing behavior.

Rust contributions must:

- use idiomatic safe Rust;
- contain no `unsafe` code;
- avoid panics and avoid `unwrap` and `expect`;
- avoid cloning unless ownership genuinely requires it;
- handle errors with useful context; and
- preserve clear module boundaries.

User-facing changes should use direct, plain language. Destructive operations
must remain deliberate and confirmed, and `--read-only` must continue to
prevent mutations.

## Running Tale during development

Run Tale against deterministic fictional data when working on the interface:

```sh
cargo run --locked -- --mock
```

This is the preferred way to exercise views without exposing or changing a
real tailnet. When live Tailscale behavior is essential, use the narrowest
permissions possible and start in read-only mode:

```sh
cargo run --locked -- --read-only
```

Do not record or commit captures containing real device names, users, domains,
addresses, routes, tokens, or other identifying network information.

## Tests

Add or update tests for every behavior change. Prefer tests of observable
behavior over tests that scan source code for particular spellings or shapes.

Useful focused commands include:

```sh
cargo test --locked --test cli
cargo test --locked --test ui_snapshots
cargo test --locked test_name
```

Use fictional, deterministic fixtures. Put external-service fixtures under the
matching directory in `tests/fixtures/`, and keep secrets and personally
identifying information out of them.

Before submitting a pull request, run the same complete gate as CI:

```sh
nix develop --command just check
```

The gate checks generated artifacts, formatting, compilation, Clippy, tests,
dependency policy, and cargo-dist configuration. A passing `cargo test` alone
is not the complete project check.

## Generated artifacts

If a change affects the command-line interface, regenerate the man page and
shell completions from their source definitions:

```sh
cargo run --locked --bin generate-artifacts -- --output-dir .
```

Commit the resulting changes under `docs/cli/` and `completions/`. Do not edit
those generated files by hand.

Release workflows generated by cargo-dist should likewise be changed through
their source configuration and regenerated, rather than edited as standalone
output.

## Pull requests

A pull request should:

- explain the user-visible problem and the behavior of the solution;
- stay limited to one logical change;
- include tests appropriate to the risk;
- mention any behavior that could not be tested locally;
- include screenshots for visible terminal-interface changes, using fictional
  data; and
- pass `nix develop --command just check`.

In the description, include the commands you ran and their results. Reviewers
may ask for a change to be split when independent concerns are combined.
